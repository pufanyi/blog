## Git 的数据模型

Git 用对象表示项目的文件状态和版本历史，用引用为提交命名。文件状态描述某个版本包含哪些路径及其内容；版本历史描述提交之间的先后与分叉关系。

### 文件、目录与快照

Git 的 **blob** 保存文件内容，即一串字节，不包含文件名。**tree** 表示一个目录，其中每个条目记录名字、文件模式和所引用的对象。普通文件条目指向 blob，子目录条目指向另一个 tree。根 tree 及其递归引用的对象确定整个项目的文件状态，称为一个快照。具体结构见 [Git 对象模型](https://git-scm.com/book/en/v2/Git-Internals-Git-Objects)。

例如，一个博客仓库包含正文和样式两个普通文件：

```text
根目录（tree）
├── article.md → 正文内容（blob）
└── style.css  → 样式内容（blob）
```

文件名属于目录条目，内容属于 blob。两份目录清单可以引用同一个 blob；一个文件改名而内容不变时，也可以复用原来的 blob。快照描述的是 Git 跟踪的文件状态，不包括未跟踪文件，也不是操作系统全部文件属性的备份。

### 提交与历史

**commit 对象**记录一个根 tree、父提交、作者、提交者、时间和提交说明。根 tree 确定这个版本的内容，父提交确定它在历史中的位置。初始提交没有父提交，普通提交通常有一个父提交，合并提交可以有多个父提交。字段定义见 [`git commit-tree`](https://git-scm.com/docs/git-commit-tree)。

提交之间的父子关系构成有向无环图。以下用 A、B、C、D 代替提交 ID，箭头均从提交指向其父提交：

```text
A ← B ← C
```

两个修改都从 B 开始，就会形成分叉。合并提交 M 可以同时以 C 和 D 为父提交：

```text
A ← B ← C ← M
    ↑       │
    └── D ←─┘
```

M 的 tree 记录合并后的文件状态；两个 parent 记录被连接起来的历史。提交图描述版本关系，目录树描述文件结构，这两种关系需要区分。

下面用两次提交表示“修改正文、保留原样式”。新 commit 指向新 tree，新 tree 引用新正文 blob；没有变化的样式 blob 被两个版本共同引用。

<SnapshotObjectsFigure />

沿 `tree` 引用可以读取一个版本的文件，沿 `parent` 引用可以遍历历史。读取某个版本的文件状态不要求按时间顺序重放每次修改。对象的物理压缩与重建放在后面的“文件存储与规模”一节讨论。

### 对象 ID 与内容寻址

blob、tree 和 commit 都属于 Git 对象。对象通过 **object ID** 标识，其他对象用 ID 引用它。在同一种对象格式下，ID 由对象类型、长度和内容计算哈希得到；相同的对象具有相同 ID。这种用内容决定地址的方式称为内容寻址，编码规则见 [Git 对象格式](https://git-scm.com/docs/gitformat-loose)。

因此，内容发生变化时，会形成新的对象，而不是覆盖原对象。例如，正文变化会产生新的正文 blob；包含它的 tree 条目随之变化，tree 也获得新的 ID。没有变化的 blob 和子 tree 可以继续复用。

commit 的 ID 还受到父提交、身份、时间和提交说明的影响。两个 commit 可以引用同一个根 tree，却具有不同 ID：它们的文件状态相同，但历史或元数据不同。所谓改写提交，是创建新的 commit 并调整引用，不是在原 ID 下修改对象内容。

### 分支、引用与 HEAD

**引用（reference）**为对象 ID 提供名称。分支引用指向一个 commit，并可以更新；commit 对象本身不随引用的移动而改变。通常附着于分支时，`HEAD` 是指向当前分支的符号引用；detached HEAD 状态下，它直接记录一个 commit ID。参见 [Git References](https://git-scm.com/book/en/v2/Git-Internals-Git-References) 和 [`git symbolic-ref`](https://git-scm.com/docs/git-symbolic-ref)。

```text
HEAD → main → C
             │ parent
             ↓
             B
```

新建分支是增加一个引用，不需要复制项目文件或历史。多个分支可以指向同一个提交，也可以共享一段历史。切换分支时如何更新工作目录，与引用本身的表示是两个层面，后面按操作分别说明。

### 读取对象与比较版本

以下命令观察一个两文件、两次顺序提交的仓库：第二次提交只修改 `article.md`，`style.css` 不变。`HEAD` 是当前提交，`HEAD~1` 是它的第一个父提交。完整的建仓步骤放在本小节末尾。

[`git ls-tree`](https://git-scm.com/docs/git-ls-tree) 列出对应快照中的目录条目：

```bash
git ls-tree --abbrev=7 HEAD~1
git ls-tree --abbrev=7 HEAD
```

两次输出依次为：

```text
100644 blob 156b3ea article.md
100644 blob 7338e12 style.css
```

```text
100644 blob 876a559 article.md
100644 blob 7338e12 style.css
```

四列分别是文件模式、对象类型、缩短后的对象 ID 和文件名。`100644` 表示普通的非可执行文件。正文的 ID 发生变化，样式的 ID 保持不变；两份清单仍然都列出两个文件。

`git cat-file -p HEAD` 显示 commit 对象。用占位名称代替实际值后，输出结构如下：

```text
tree <根 tree 的 ID>
parent <父 commit 的 ID>
author <作者及时间>
committer <提交者及时间>

Explain the opening example
```

读取旧正文时，Git 从旧 commit 找到根 tree，再按 `article.md` 查找 blob。对应的命令是：

```bash
git show HEAD~1:article.md
```

<ReadVersionFigure />

`show` 显示所选内容，不覆盖工作目录中的文件。比较两个版本的正文则使用：

```bash
git diff HEAD~1 HEAD -- article.md
```

diff 是对两个版本内容的比较结果。commit 记录快照引用和历史信息，并不保存这份逐行差异。

<details>
<summary>复现这个两文件实验</summary>

在一个新目录中运行下面的命令。需要已经配置 Git 的提交姓名和邮箱。例子没有设置内容转换规则，两个文件都作为普通文本保存。

```bash
mkdir blog-snapshot-example
cd blog-snapshot-example
git init

cat > article.md <<'ARTICLE'
# Version Control

修改文章后，提交保存。
ARTICLE

cat > style.css <<'STYLE'
body { line-height: 1.8; }
STYLE

git add article.md style.css
git commit -m "Write the opening"

cat > article.md <<'ARTICLE'
# Version Control

修改文章后，提交保存，之后可以比较和找回旧版。
ARTICLE

git add article.md
git commit -m "Explain the opening example"
```

然后执行正文中的 `ls-tree`、`cat-file`、`show` 和 `diff` 命令。本节展示的缩写来自 SHA-1 格式的仓库；使用 SHA-256 的仓库会得到不同 ID。文件的空格、换行和编码也会影响 blob ID，提交的身份和时间则会影响 commit ID。观察的重点是：文章内容变了，样式内容没变，它们的对象 ID 是否相应变化。

</details>

## Git 的操作与状态变化

### 工作目录、暂存区与提交

Git 的日常操作涉及三种状态：

| 状态 | 含义 |
| --- | --- |
| 工作目录 | 当前供编辑器、编译器等程序读写的文件 |
| 暂存区（index） | 准备写入下一次提交的文件状态 |
| 当前提交 | 已记录的版本，由 HEAD 确定 |

在没有合并冲突的普通工作区中，index 记录路径、文件模式、选定的 blob ID 和缓存信息等。它包含未修改的已跟踪文件，而不只包含“这次改过的文件”。

### add 与 commit

[`git add article.md`](https://git-scm.com/docs/git-add) 保存执行那一刻选中的正文内容，并更新 index 中的对应条目。之后继续编辑正文，需要再次暂存，新的编辑才会进入下一次普通提交。

例如，正文已经改好，样式仍在试验；只暂存正文，就会选中“新正文 + 原样式”：

<StagingSelectionFigure />

不带路径或 `-a` 的普通 `git commit` 根据 index 生成目录树，创建指向它的新 commit，并在附着于分支的状态下更新当前分支引用。样式试验仍留在工作目录中。

```bash
git add article.md
git ls-files --stage
git commit -m "Explain the opening example"
```

[`git ls-files --stage`](https://git-scm.com/docs/git-ls-files) 可以观察 index 中的文件模式、对象 ID 和 stage 编号。暂存选择的是内容；提交把这份选择记录为一个版本。

### diff 的比较对象

| 命令 | 比较的两端 |
| --- | --- |
| `git diff` | index 与工作目录 |
| `git diff --cached` | HEAD 与 index |
| `git diff HEAD` | HEAD 与工作目录 |
| `git diff A B` | 提交 A 与提交 B |

前两项分别显示尚未暂存和已经暂存的变化。这里讨论已跟踪文件的普通修改；未跟踪文件不会自动成为 `git diff` 的比较内容。

## 文件存储与规模

### 对象复用与压缩

版本模型、差异展示和物理存储是三个层次：

| 层次 | 内容 |
| --- | --- |
| 版本模型 | commit 引用根 tree，根 tree 确定文件状态 |
| 差异展示 | 比较两个版本的内容，生成 diff |
| 物理存储 | 复用相同对象，对不同对象进行压缩和组织 |

文件内容不变时可以复用 blob；子目录的条目不变时可以复用 tree。完整快照不意味着每次提交都复制整个项目。

Git 通常先把新对象保存为单独的 [loose object](https://git-scm.com/docs/gitformat-loose)，之后可以通过维护操作将它们整理进 packfile。新旧正文虽然是不同的 blob，仍可能包含大量重复字节。[packfile](https://git-scm.com/book/en/v2/Git-Internals-Packfiles) 可以保存基准对象和 delta，用重建指令复用相似内容。

<DeltaStorageFigure />

存储上的基准依赖不要求与 commit 的父子关系一致，基准也不必是历史上更早的版本。读取对象时可能需要解压和重建，重建后仍然得到原 ID 标识的完整对象。压缩不改变 commit、tree 和 blob 的逻辑引用关系；具体编码见 [pack 格式](https://git-scm.com/docs/gitformat-pack)。

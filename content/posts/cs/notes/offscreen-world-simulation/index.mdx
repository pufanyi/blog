出门探险之前，我们在基地里种下一块田，点燃一座熔炉，又把食物放进箱子。走远十分钟，再回来：庄稼成熟了吗？熔炉烧完了吗？食物腐烂了吗？附近的怪物还在原来的位置吗？

直觉上，这些问题似乎取决于同一个开关：基地有没有被“加载”。但 Minecraft、泰拉瑞亚和饥荒恰好说明了，这个开关往往并不存在。

一块地形可以留在内存里，却不执行某类更新；一个实体可以停止 AI，却仍有计时任务；远处一座山可以继续显示，而它的完整场景已经被卸载。甚至“回来后发现庄稼长了”，也不能证明离开期间程序一直在模拟它——结果可能是在回来那一刻计算出来的。

要理解大世界如何工作，我们需要追踪两件事：**状态保留在哪里，以及哪些状态变化值得继续计算。** 下文先用三款游戏建立这套理解，再看 Unreal Engine 的 World Partition、HLOD、Mass，以及 Factorio 提供的另一条优化思路。

## “加载范围”实际上混合了五个问题

假设远处有一座村庄。我们关心的不只是能不能看见房子，还包括村民有没有走动、商店有没有补货，以及烧毁的房子会不会在重新进入时恢复原样。

这些需求对应不同的工作：

| 问题 | 程序需要做什么 | 可以独立省掉什么 |
| --- | --- | --- |
| 数据是否驻留 | 把地形、对象状态放在内存中 | 远处数据可以留在磁盘，按需读入 |
| 画面是否显示 | 提交模型、材质、动画和粒子 | 看不见的内容可以不画，远景可以用简化代理 |
| 逻辑是否推进 | 执行 AI、碰撞、生产、生长等更新 | 可以停更、降频、按事件更新或补算 |
| 客户端是否收到 | 向某位玩家同步有关状态 | 服务器仍可运行，只是不向这个客户端发送 |
| 状态是否持久保存 | 记录地形修改、库存、角色等 | 可以保存少量语义状态，而非全部运行时对象 |

它们不是严格套在一起的五个同心圆。远程工厂可能需要模拟，却不需要向你发送每个机器的动画；远山需要显示，却不需要每棵树的完整交互对象。多人游戏还会出现：你已经离开基地，另一个玩家仍然在那里。

先约定两个术语。**Tick** 是游戏推进逻辑的一次离散更新，不等同于画面的一帧。**权威状态** 是最终决定“事情到底发生了什么”的那份状态；联机游戏通常由服务器维护它，单人游戏也可以在本机运行相应的逻辑。

优化因此有两个不同目标：让内存容纳有限的数据，让 CPU 在有限时间里完成必要的更新。把模型画得更简单，主要缓解渲染负担，并不会自动让远处的 AI 更便宜。

## 第一种选择：只让部分空间拥有模拟资格

### 为什么 Minecraft 需要区块

如果世界可以不断向外生成，试图把所有已经探索过的地形一直放在内存里，成本会随探索距离增长。一个自然的办法是把世界拆成 **chunk**：以区块为单位生成、加载、保存和卸载。

但“已经读进内存”仍不足以决定一辆矿车要不要移动。服务器还需要判断某个区块是否进入相应的模拟范围。Minecraft Java 版通过 **ticket** 表达保持区块加载或模拟的需求。玩家是一种需求来源，强制加载等机制也可以提供需求；1.21.5 的 ticket 结构明确区分用于加载和用于模拟的用途。[@mcTickets]

可以把它理解为一张申请单：“这个区域接下来仍然有用，请保留相应资源。”申请失效，并且没有其他需求接替时，区域才有机会退出相应活动状态。这里描述的是职责，不是把所有版本的内部状态简化成一个布尔值；方块、方块实体和普通实体的更新资格还需要分别考虑。

<WorldActivity />

图中右侧孤立的活动区域很重要：**一个世界的活动范围可以由多个来源共同决定，而不只围绕当前玩家。** 这正是区块加载器和多人分散活动能够改变服务器负担的原因。增加活动区块，省下的计算就会重新出现。

### 不同更新机制，并不共享全部条件

为了判断基地会发生什么，还要区分更新的性质。

一个持续运动的实体，需要反复更新位置与碰撞；一种需要按逻辑刻推进的方块实体，需要获得对应的 tick；作物生长则可能通过 **random tick** 获得变化机会。Random tick 是抽样执行一部分方块更新的机制，不能简单等同于“每个方块有一个真实时间倒计时”。

因此，对停止获得逻辑更新的普通过程，不能指望重新进入时自动重演离开的每一刻。Minecraft 并没有一个把所有区块内容统一快进十分钟的通用恢复规则。保存状态、恢复待处理任务，与补做离开期间的全部 AI、碰撞和生产，是不同的承诺。具体对象若另有计时或恢复规则，还要继续检查该对象。

这里有两个容易让旧教程失效的版本变化：

| Java 版变更 | 对理解机制的影响 |
| --- | --- |
| **1.21.5**：随机刻不再只限于玩家周围原先的 8 区块范围；玩家模拟距离内，以及末影珍珠等其他区块加载来源保持加载的区域，也可以收到随机刻 | 不能继续笼统断言“没有玩家，加载器也无法让作物生长”；仍须满足作物自身条件 |
| **1.21.9**：移除了固定的 spawn chunks | 不能再把“出生点周围永久保持活动”当作所有新版 Java 世界的基础规则 |

这两条分别来自官方正式版发布说明。1.21.5 的说明还把自然刷怪等机制与随机刻分开；所以“作物可以长”也不推出“刷怪塔一定照常工作”。[@mc1215; @mc1219]

这揭示了设计上的一个取舍：空间边界很适合限制精细模拟成本，但一套机器可能跨越边界。若只让一半获得必要更新，整体行为就可能与全部活动时不同。设计、排查自动化设施时，应检查完整的依赖范围，而不是只确认中心位置已经加载。

### 基岩版：相同问题，另一套具体规则

基岩版的官方文档同样区分 render distance 与 simulation distance，并提供 **ticking area**，让指定区域在没有玩家靠近时保持活动。文档特别指出：区域可以保持活动，但自然刷怪仍有玩家条件；活动实体离开 ticking area、又不在玩家模拟范围内时，会停止移动。[@mcBedrock]

所以，Java 的 ticket、基岩版的 ticking area，可以放在同一张“谁请求模拟”概念图里理解，却不能直接互换具体范围、命令和更新规则。

## 第二种选择：地图留着，每次只处理少量位置

Minecraft 的空间策略不是唯一选择。若地图本来就是有限大小，地形数据又比较紧凑，另一个方案是：保留整张地图的逻辑表示，再分别控制各种更新的成本。

### 泰拉瑞亚的屏幕边缘，不是世界逻辑的边界

在核对的 PC 代码中，泰拉瑞亚用覆盖世界坐标范围的 tile 结构保存地形。原版快照的 `Main.tile` 是二维数组；tModLoader 将其改成自己的 `Tilemap`，因此不能拿模组框架的布局推断原版每格的内存大小。这里关心的是两者都提供整张有限地图的坐标访问。[@terrariaMain; @tmlMain]

更关键的是 `WorldGen.UpdateWorld()` 的取样范围：它分别在地表区域和地下区域随机选坐标，横向范围跨越世界，而不是只从玩家视野附近取点。抽样数量随世界面积和更新速率变化，再交给对应 tile 的生长、传播等逻辑处理。[@terrariaWorld] tModLoader 的公开补丁在这些世界更新入口接入了模组回调，[@tmlWorld] 对应的 `RandomUpdate` API 也明确用于生长、传播等随机更新。[@tmlRandom]

这就解释了为什么“我不在附近”不能作为远处植物停止变化、环境停止传播的可靠依据。它们的更新机会可以来自世界级抽样，而不是从进入镜头的瞬间才开始出现。

但这也不意味着每个 tile 每帧都运行完整逻辑。我们可以用一个**简化抽样模型**看清节省来自哪里：假设某一区域有 $N$ 格，每一轮独立、有放回地抽 $m$ 次。

对其中一格，一次没被抽到的概率是 $1-1/N$；连续 $m$ 次都没被抽到的概率，就是这些独立概率相乘。所以它这一轮至少得到一次机会的概率为

$$
P(\text{被抽到})=1-\left(1-\frac{1}{N}\right)^m.
$$

当 $m$ 远小于 $N$ 时，这大约等于 $m/N$。程序把一轮的候选检查量从 $N$ 降到 $m$，同时允许整个取样区域逐渐变化。若希望不同尺寸地图上每格获得机会的频率接近，就要让 $m$ 随 $N$ 增长。

这只是解释抽样成本的模型。泰拉瑞亚实际区分高度区域、世界类型和 tile 自身条件；“被抽中”也不等于“成功生长”。不能用这个式子直接计算某棵树多久长大。

### 地形更新、实体活动和网络分区，需要分开看

怪物不是 tile。NPC 有自己的活动状态和清理规则。公开补丁里的 `CheckActive` 路径就包含超时、不再活动后的移除逻辑，城镇 NPC 又有单独处理。怪物离开后消失，可能是 **despawn**：实例被清理了；它与“保存原来那只怪物，回来后继续更新”有不同语义。[@tmlNPC]

液体、电路、tile entity 也有自己的更新入口，不能从随机 tile 更新推出所有系统都按同样的频率或范围运行。核对的 `UpdateWorld()` 中，这些入口与地形抽样是分开的。[@terrariaWorld]

联机时也要区分服务器的地图与客户端收到的数据。网络上的分区传送解决“给玩家发送哪些地形”，并不能反过来证明服务器把其他区域的权威状态卸载了。

因此，泰拉瑞亚带来的核心启发是：**让完整世界状态可访问，与让完整世界每一刻都执行所有逻辑，是两个独立选择。** 对有限、紧凑的二维地图，保留状态、稀疏更新，是很有吸引力的组合。

## 第三种选择：对象休眠，由组件决定时间怎么走

如果对象有很多不同的职责，只按空间一刀切，还会损失一些本来容易保留的行为。

例如远处一只动物的寻路可能很昂贵，箱子里食物的新鲜度却只是少量数值。如果把它们全部停掉，玩家会得到“离开就永远保鲜”的世界；如果全部照常精细模拟，又浪费大量计算。

### 饥荒的实体休眠，不是整个区域一起消失

饥荒联机版的 Lua 层提供了一个很清晰的观察窗口。在核对的脚本中，`OnEntitySleep` 会停用实体的 brain、让 state graph 休眠，然后调用各组件自己的休眠回调；唤醒时再执行相应恢复。[@dstMain]

这里的 sleep 是引擎管理对象活动的休眠，不是角色中了催眠效果、在床上睡觉。脚本对象仍可以保留状态，也可以继续持有定时任务。至少在这条回调路径上，它不是 Minecraft 式的“整个区块序列化后从内存移走”。

**组件（component）** 可以理解为附着在对象上的一种职责：生长、腐败、燃烧、战斗等。休眠回调把决定权交给这些职责，各自回答“远处还需要保留什么行为”。

| 核对到的机制 | 休眠之后怎么处理 | 不能由此推出什么 |
| --- | --- | --- |
| brain 与 state graph | 停止相应常规活动，醒来恢复 | 不能推出该实体的所有计时任务也停止 |
| `growable` | 普通路径可以取消生长任务，记录休眠时间，醒来调用 `LongUpdate`；也有 `growoffscreen` 分支 | 不能把所有植物、所有生长阶段都归为同一条路径 |
| `perishable` | 通过周期任务推进腐败，另外提供长时间更新入口 | 不能说所有食物都等到玩家回来才开始计算腐败 |

`growable` 的代码明确保留了普通休眠补算与 `growoffscreen` 两条分支。[@dstGrowable] `perishable` 则以约十秒、带少量扰动的周期，结合容器、温度等条件处理剩余新鲜度。[@dstPerishable] 调度器并没有一个因为实体睡眠就自动取消全部普通任务的统一开关。[@dstScheduler]

这里已经有三种不同的省钱方式：AI 停止，数值低频更新，部分进度醒来补算。它们可以出现在同一个世界，甚至同一个对象上。

### 为什么不能用一句“饥荒会补算”解释所有事情

`LongUpdate(dt)` 的作用是把一段经过时间交给明确支持它的逻辑。实体的分发函数只调用实现了相应方法的组件；引擎不会自动理解每个组件应该怎样跨过这段时间。[@dstEntity]

而且，组件之外还有 prefab 自己的处理。**Prefab** 是某类具体对象的构造与行为组合。核对的常青树脚本在休眠时会移除燃烧、传播等组件；对于正在燃烧的树，还可能先标记烧毁状态，醒来再恢复对应表现。这个具体规则足以说明：不能把远处森林当作一套与近处完全相同、持续逐帧进行的火焰传播模拟。[@dstEvergreens]

检查某个现象时，应沿着下面这条链找：

> 具体 prefab → 使用哪些组件 → 是否注册定时任务 → 休眠时取消什么 → 唤醒或 `LongUpdate` 时补什么。

只搜到组件有一个 `LongUpdate` 方法，还不足以证明某次离开真的走了这条路径，更不足以证明结果与逐帧运行一致。

### 单机版跨洞穴，与联机版的远处对象又是两回事

单机版的历史脚本提供了另一种时间推进：在上下洞穴、重新载入世界时，比较玩家与世界记录的年龄，计算差值，再调用 `LongUpdate` 追赶。这里是在恢复一份落后的世界状态。[@dsCatchup]

联机版则有 **shard**：不同世界由不同服务器实例管理。官方服务器指南说明了多世界分片和 `pause_when_empty` 配置。因此，“我进了洞穴”不等于“地面服务器被卸载”；地面有其他玩家、服务器仍在运行，和恢复一个暂停的单人世界，是不同情况。[@dstServer]

还有一个容易混淆的时钟：Lua 中的 `GetTime()` 来自模拟 tick，而不是电脑挂钟。现实中过了十分钟，不保证游戏也前进了十分钟。暂停、服务器停止运行，以及主动执行长时间推进，都必须分别考虑。[@dstMain]

## 到底什么东西能够便宜地补算

现在可以从实现回到设计。假设我们希望基地的一座磨坊在玩家离开后继续生产。

### 先找出真正决定结果的状态

先给磨坊一个简单规则：每 $30$ 秒生产一袋面粉，原料无限，仓库足够大，没有停电。离开时已经完成本轮的 $12$ 秒，再经过 $600$ 秒，相当于有 $612$ 秒生产时间可结算。

每完整 $30$ 秒产生一袋，因此新增产量是

$$
\left\lfloor\frac{12+600}{30}\right\rfloor=20,
$$

余下的 $12$ 秒保留为下一轮进度。我们只需要生产速率、上次结算时间、剩余进度和产量，不需要补跑几万次 tick。

<TimeStrategies />

这种计算有效，是因为刚才把会改变速率和终止条件的因素都固定了。加入库存上限后，产量必须在仓库装满时停止；加入原料后，还要在原料耗尽时停止；加入停电后，就只能累计有电的时段。不能先算出无限产量，再随便截断，因为停产期间是否积累进度，本身就是游戏规则。

更一般地，若生长速度 $r$ 随环境改变，进度要累计的是每段时间的有效速度。离开期间先温暖、后入冬，就应按两个时段分别处理。用数学记号表达，这要求计算

$$
\Delta g=\int_{t_0}^{t_1}r\bigl(e(t)\bigr)\,dt,
$$

其中 $e(t)$ 表示当时的环境。如果只记下返回时的温度，再乘以整个离开时间，就丢掉了历史。实现可以保留环境变化事件，或者主动选择一个更便宜的近似规则；两者应当在设计上说清楚。

### 战斗为什么难得多

两只怪物互相攻击时，下一次位置依赖上一次碰撞，攻击结果依赖距离、目标、冷却和随机数。中间还可能有人加入、桥被拆掉、弹丸碰到第三个对象。

这些相互作用很难压缩成“经过时间乘一个速率”。只知道起点、终点和经过时间，通常不足以重建中间的因果链。

可以换一种规则：远处只记录两个群体的人数、实力和交战状态，按较粗的模型决定损失；靠近后再生成具体个体。这样确实能省钱，但它是 **simulation LOD**，即改变模拟细节，而不是对原有精细模拟进行数学上完全等价的加速。玩家可能观察到不同结果，设计必须容许这种差异。

所以补算的前提不是“玩家没看见”，而是：**我们保留的少量状态，是否足以决定之后承诺给玩家的结果。**

## 现代大世界：把不同精度的表示组合起来

前面的三种选择并没有随引擎发展而消失。现代大世界通常把它们用于不同层次，再增加预加载、远景代理与联网相关性管理。

### World Partition：先解决完整场景放在哪里

Unreal Engine 的 World Partition 将世界划分为可流式加载的 cell，根据 **streaming source** 加载附近区域。玩家可以是来源，传送目的地也可以临时放置一个来源，先等目标区域准备完成，再让玩家过去。[@uePartition]

这比“走到边界才开始读盘”多考虑了一件事：资源到达需要时间。即使总内存够用，读取、解压、创建对象和准备图形资源也可能形成卡顿。

一个简单的工程估算是：若玩家最大移动速度为 $v$，从请求到可交互的准备时间为 $L$，那么前方预取距离至少应覆盖约 $vL$，再留出抖动余量。这是设计估算，不是 Unreal 的固定公式。高速载具、突然传送和不稳定 I/O 都会使单纯按当前位置取一个圆不够用。

为了避免站在边界来回移动时反复装卸，还可以设置不同的进入、退出阈值：靠近到较小距离时加载，远离到较大距离时才卸载。这种 **hysteresis** 用一点额外驻留内存换取稳定性。

### HLOD：原来的房子卸载了，为什么还能看见城市

如果卸载完整场景就让所有东西消失，视野会被限制在很近的地方。可远处一整片城区，只占屏幕上很少的像素，并不需要每扇门、每个室内物件都存在。

**HLOD** 把一组静态对象合并或简化为便宜的代理表示。Epic 的文档明确把它用于显示尚未加载的 World Partition cell：完整的原对象不在，代理模型仍在。[@ueHLOD]

于是，“能看见那座房子”不再能证明房子里的 NPC、碰撞、脚本和可拾取物都已加载。代理本身仍然需要资源，只是比完整场景便宜。至于房屋着火、被拆除后远景如何更新，仍需要游戏维护代理与权威状态的一致性。

### Mass：画面、模拟和同步可以各有一档精度

对大量人群，单靠静态场景分区还不够。Unreal 的 MassGameplay 分别提供视觉表示、模拟和 replication 的 LOD：视觉可以在不同 Actor、实例化网格及无表示之间切换；模拟可以采用可变更新频率；同步相关性则按每个连接的客户端分别判断。[@ueMass]

这让同一个行人可能同时处于这样的状态：服务器用低频逻辑推进；某位远处玩家只收到稀疏信息；另一位近处玩家看到完整表现。

但这些是可供开发者组合的机制。框架不会自动替游戏决定“远处战斗应该怎样结算”，也不会自动保证不同精度转换后的剧情和经济状态合理。

### Factorio：有些东西必须远处也运行，那就减少无用工作

工厂游戏给出了一个重要约束：如果玩家离开，生产线就完全停止，会破坏远程建厂的玩法。此时距离未必是最好的优化依据，应当继续问“哪些对象现在真的有变化需要处理”。

Factorio 的开发日志记录过一个具体改动：将雷达覆盖从各对象反复请求维持，改成在地图区块上注册覆盖计数。覆盖重叠只增加计数，再把相关区块分桶更新；最后一个覆盖来源消失后，移出更新集合。[@factorio421]

这是一个值得迁移的想法：**先表达依赖，再处理依赖变化。** 如果一个设备正在等待输入，可以由输入到达触发工作；如果很多设施请求相同区域保持某种状态，可以合并请求。是否能这样优化，取决于系统能否完整捕获唤醒条件；漏掉一个事件，就可能让设备永久“睡死”。

所以，大世界的计算预算既可以按空间分配，也可以按活动性、依赖关系和玩法重要性分配。

## 如果自己设计一个大世界，应该怎样组合

回到那座包含农田、磨坊、村民和怪物的村庄。现在我们可以逐步为它设计策略。

**首先，保留玩家真正改变的事实。** 房屋是否烧毁、仓库库存、村民身份和任务状态，是持久数据。模型实例、动画播放位置、临时寻路缓存通常不需要以相同方式保存。对程序生成地形，可以考虑保存生成依据与玩家修改；但必须同时固定生成规则的版本，否则升级后同一个种子未必重建出相同的底图。

**然后，把远处仍有价值的进展表示成少量状态。** 农田记录生长阶段和相关环境事件，磨坊记录库存与生产进度，商队记录路线和预计到达事件。不要为了保留一个到达时间，让整支商队始终逐帧寻路。

**接着，确定哪些相互作用不能被省略。** 玩家正在交战的怪物需要精细逻辑；远处一个会改变任务结局的袭击，可以由经过设计的粗略规则处理。若游戏承诺子弹能够从活动区域飞向远处，就必须让弹丸即将接触的区域提前获得足够的碰撞与模拟数据。

**最后，给状态转换写清楚规则。** 从抽象商队恢复成具体车辆时，货物只能属于一份权威状态。不能让抽象层结算一次卸货，具体实体生成后再卸一次；也不能因为换了表示就重新生成已被抢走的物资。

下面是一种可行的组合，属于设计示例，并非上述任何一款游戏的完整实现：

| 对象 | 玩家附近 | 玩家远处 | 返回时要恢复什么 |
| --- | --- | --- | --- |
| 山体与建筑外观 | 完整场景与必要碰撞 | HLOD 或更粗的地形表示 | 与已保存破坏状态一致的场景 |
| 农田 | 可见生长阶段与交互 | 环境事件加生长进度 | 阶段、产物和剩余进度 |
| 磨坊 | 生产逻辑与动画 | 库存约束下的计时或事件结算 | 同一份库存及当前生产批次 |
| 商队 | 具体移动、避障和交互 | 路线状态与途中事件 | 位置、身份、货物与损失 |
| 普通怪物 | 精细 AI 与碰撞 | 休眠、清理或群体近似，按玩法选择 | 保留个体，或按明确规则生成新个体 |

### 真正困难的地方经常在边界

空间分区解决了组织问题，也创造了交接问题。

一条河流跨越两个区域，活跃的一侧如何与暂停的一侧交换水量？两个服务器分别管理边界两侧，一件掉落物跨过去时，谁负责保存它？一个预加载任务在玩家已经转身后才完成，还要不要创建对象？

这些问题共同要求三件事：

1. **明确所有者**：同一时刻，谁有权修改这份状态。
2. **明确边界规则**：跨边界的作用是继续传播、排队等待、截断，还是用近似处理。
3. **限制转换成本**：不要把平时省下的所有计算堆到返回的一帧；资源准备和对象恢复也要分批执行。

多人游戏还要把“服务器需要运行什么”和“某个客户端需要知道什么”分别调度。两位玩家位于地图两端，服务器的活动集合可能扩大，而各自收到的状态仍可只覆盖相关区域。单纯减少网络发送，并没有减少权威世界的模拟工作。

## 用一张表重新回答最初的问题

这里的“离开”指离开对应活动范围，但世界时钟仍在运行。若整个游戏暂停或服务器关闭，需要另行考虑。

| 游戏或机制 | 远处主要发生什么 | 回来时为什么会看到变化 |
| --- | --- | --- |
| Minecraft Java | 由区块需求和具体更新资格决定；失去相应资格的过程停止获得更新，其他玩家或加载来源可保留活动 | 可能一直在其他来源维持的区域中运行；不能默认有统一离线补算 |
| 泰拉瑞亚 | 有限世界的 tile 状态可访问；地形随机更新可覆盖远处，NPC 等系统各有规则 | 相关逻辑可能在离开期间持续获得稀疏更新 |
| 饥荒联机版 | 实体休眠与组件策略结合；AI、周期任务、生长补算不必同进同退 | 可能是低频任务持续推进，也可能是特定组件醒来结算 |
| 现代流式场景与 simulation LOD | 按需保留完整对象，远处使用代理、低频逻辑或抽象状态 | 完整表示从持久状态及后台进展中恢复 |

最初那四个问题，因此没有一个跨游戏通用的“加载了就继续，没加载就暂停”的答案。庄稼、熔炉、食物、怪物，需要分别找到自己的更新路径。

<summary>怎样在自己的存档里区分这些机制</summary>

以下是实验设计建议，不是本文已经执行的实测结果。

先固定版本、模组、世界规则和服务器暂停配置，记录游戏时间，再比较“留在附近”“走远但世界继续运行”“另一玩家留守”“整个世界暂停”四组条件。注意控制光照、季节、原料和库存，否则会把生产条件变化误判成加载机制。

对随机生长，应观察多株、多次实验；一株没长不能证明它没有更新。对实体，要记录身份，避免把新刷出的同种怪物当成原来的实例。

仅凭回来时的终态，往往分不出后台更新与唤醒补算。若有调试能力，应记录权威端的休眠、唤醒、周期任务及长时间更新调用；调试观察本身也要避免加载或唤醒目标区域。

大世界之所以能显得一直存在，是因为“存在”可以有不同成本：一份磁盘记录、一个库存数字、一条将来到期的事件、一个远景代理，或者一个正在精细模拟的实体。

设计的关键是先决定玩家应当观察到哪些连续性，再为这些连续性保留足够的状态与计算。世界不必在所有地方、所有时刻拥有同样的细节，但每次从一种表示切换到另一种表示时，都应该仍然是玩家刚才离开的那个世界。

假设我们要做一个可以自由旅行的世界。玩家从村庄骑马出发，穿过森林，再登上山顶：近处需要树木碰撞和动物活动，远处要看得见城市；留在村里的磨坊仍应生产，另一名玩家也可能正在那里交易。几小时后回来，仓库里的货物、被砍掉的树和已经完成的任务，都应该接得上。

最直接的实现，是把所有东西加载进来，每一刻都完整运行。但地图越大、对象越多，这种做法越难承受。于是我们会问：哪些东西可以卸载？哪些可以少算？哪些只需要记住结果？不同表示之间又怎样交接？

这些问题很难由一款游戏、一种空间分区或一个“加载半径”全部解决。飞行游戏需要提前准备极远的地形，工厂游戏需要持续运行远处的生产线，联网射击游戏需要准确处理附近的交战。它们承诺给玩家的行为不同，合理的架构也会不同。

本文沿着一个大世界从“装不下”到“算不完”，再到“多人之间必须一致”的过程展开。World Partition、HLOD、Nanite、Mass、ECS，以及 Minecraft、泰拉瑞亚、饥荒和 Factorio，会在它们能够说明具体机制的地方出现。重点是理解每种方案省掉了什么工作、留下了什么状态，以及必须承担什么代价。

## 世界有多大，究竟大在哪里

### 先分清五种工作

一块区域“存在”，可以意味着很多事情：它在存档中有记录，它的模型在显存里，它的角色在思考，或者某位玩家刚收到它的状态。这些并不总是同时发生。

| 问题 | 主要消耗 | 常见控制手段 |
| --- | --- | --- |
| 完整数据是否驻留 | 内存、显存 | 分区、按需加载、缓存与淘汰 |
| 画面需要多少细节 | GPU 时间、绘制准备成本 | 可见性裁剪、LOD、实例化、代理表示 |
| 逻辑是否需要推进 | CPU 时间 | 活动集合、事件驱动、降频、补算、简化模型 |
| 谁需要收到变化 | 带宽、同步准备的 CPU 时间 | 相关性筛选、增量同步、网络休眠 |
| 哪些变化必须记住 | 存储、保存与恢复成本 | 稳定身份、快照、修改记录、状态迁移 |

这里的 **LOD** 是 level of detail，即细节等级。**Tick** 是逻辑推进的一步，不等于一帧画面。**权威状态** 则是发生冲突时，用来决定游戏事实的那份状态；在常见的服务器权威架构中，由服务器维护它。

一座远山可以只剩可绘制的代理；一条远程生产线可以只保留库存和生产状态；网络上的一棵树可以很久不发送消息，却继续留在客户端内存里。因此，这五种工作应当分别调度。

还要区分**世界的总规模**与**当前活跃密度**。几万平方公里的空地，可能比一间塞满可碰撞物体、脚本和角色的小仓库更容易运行。地图面积、资产体积、同时交互的对象数和玩家分布，衡量的是不同压力。

### 预算既限制总量，也限制到达时间

假设目标是每秒显示 $60$ 帧，每帧约有 $16.7$ 毫秒。这个数字不是一张可随意分配给所有线程的总账单：CPU 与 GPU 会流水工作，但关键路径上的一段长任务，仍可能推迟整帧。

内存充足，也不能保证场景及时准备好；平均帧率很高，也不能保证跨进新区域时不卡。大世界至少需要同时管理：

- **驻留预算**：已经加载的资源、尚在解压的数据、过渡期间的新旧表示，都占空间。
- **持续预算**：当前这些对象，每秒需要多少模拟、渲染与同步工作。
- **转换预算**：这一帧最多能够创建、恢复、激活或销毁多少东西。

后面每一种优化，都要放回这三种预算里检查。仅仅把平时的计算推迟到玩家返回时，可能会把持续压力变成一次很长的卡顿。

## 让需要的区域及时到场：分区与流式加载

### 为什么要分区，为什么区块也不能无限小

如果世界数据是一整个不可拆的文件，访问其中一条街道也可能牵动整张地图。分区先把数据切成能够独立管理的单元，再为每个单元记录范围、资源依赖和驻留状态。

最容易理解的是规则网格。它适合快速把位置映射到 cell，也方便表达附近区域。密度差异很大时，还可以考虑分层网格、树状空间索引，或按室内房间、场景语义组织。空间索引负责快速找到候选对象；被找到以后需要加载多少内容，仍由资源组织决定。

分区越大，一次请求可能带入越多用不到的内容；分区越小，请求数量、索引、调度和跨边界依赖又会增加。一个巨型建筑若被机械地切成很多小块，却必须一起出现，小块并没有真正获得独立性。

Unreal Engine 的 **World Partition** 提供了具体实现：用可流式加载的 cell 管理大场景，并根据 streaming source 的位置与需求选择区域。玩家可以是来源，传送目的地也可以先放置临时来源，准备好后再移动玩家。[@uePartition]

<WorldActivity />

由此得到的活动集合可以有多个分离区域。附近没有玩家，也可能因为任务、远程摄像机或其他系统的需求而保持某种活动。反过来，“数据已经加载”并不要求所有逻辑立即开始执行。

<details>
<summary>案例：Minecraft 把空间需求表达为 ticket</summary>

Minecraft Java 版用 ticket 表达保持区块加载或模拟的需求。NeoForge 的 1.21.5 迁移说明明确区分了 ticket 用于加载和用于模拟的用途；玩家和强制加载等机制可以提供不同来源。[@mcTickets]

这是一种值得借鉴的需求管理方式：某个使用者离开，不代表区域立即失效，还要看其他需求是否仍然存在。具体机制仍有额外资格，不能把“区块已加载”理解成所有方块、方块实体和普通实体都以相同方式运行。

游戏规则也会变化。Java 1.21.5 扩大了随机刻的适用范围，包括玩家模拟距离及末影珍珠等其他加载来源保持的区域；自然刷怪等机制仍有不同条件。[@mc1215] 1.21.9 又移除了固定出生区块。[@mc1219] 基岩版则有独立的 ticking area 机制，不能直接套用 Java 的 ticket 规则。[@mcBedrock]

这些版本差异说明：空间调度提供的是运行资格，具体系统怎样使用资格，仍属于游戏规则。

### 读完文件，只完成了加载链的一部分

考虑村庄里一间房子的出现过程。系统首先决定需要它，然后读取和解压资源，创建对象，建立渲染、物理等系统中的表示，恢复游戏状态，最后才让它参与交互。

这是一个有依赖关系的流水线。将文件读取放到后台线程，只覆盖了其中一段。如果一万件资源同一时刻读完，紧接着集中创建对象、注册碰撞，主线程仍可能突然承受巨大压力。

<StreamingPipeline />

实际设计应为不同阶段设置预算：限制并发读取和临时缓冲，分批创建和注册对象，优先准备地面碰撞、关键交互与可见轮廓，再补上次要细节。玩家突然改变方向后，还要取消不再需要的请求，或至少避免把过期结果继续激活。

这里有一个重要区别：**异步**让工作可以与其他工作重叠，**分帧或分批**限制一次提交给关键路径的工作量。它们能够配合使用，但不能互相替代。

这也是现代引擎继续优化的方向。Epic 在 UE 5.6 的发布说明中，将静态内容流送改进与物理状态的异步创建、销毁一起列出；其中 Fast Geometry Streaming 在该版本仍标为实验功能，面向不可变的静态几何。[@ueStreaming56] 它说明优化已经深入到对象生命周期，而不是只提高读盘速度；也不能把针对静态几何的收益直接外推到任意可交互对象。

对于大量依赖**程序化生成（PCG）**的世界，加载管线的瓶颈会有所不同。生成区块通常消耗大量的 CPU 或 GPU 算力，而非单纯的 I/O。这种“流式计算”同样需要纳入转换预算的框架，严格切分时间片以避免算力峰值阻塞主线程。

### 提前多久开始，退后多远才释放

设玩家前进速度为 $v$，从发出请求到区域可交互需要 $L$ 秒。那么仅仅为了覆盖这段准备时间，前方就需要约 $vL$ 的提前量。

例如，速度为 $30\,\mathrm{m/s}$，准备时间为 $0.8\,\mathrm{s}$，就已经需要约 $24$ 米。实际还要留出排队与 I/O 抖动余量。因此一个更实用的估算是

$$
D_{\mathrm{prefetch}}\gtrsim vL+\text{安全余量}.
$$

这是设计估算，不是任何引擎的固定公式。路径可预测的列车，可以沿轨道预取；高速自由飞行需要更大的候选范围；传送则通常要先准备目的地，再完成位置切换。

离开时也不宜立即释放。可以设置不同阈值：进入较近范围时申请加载，离开更远范围才申请卸载。这种 **hysteresis** 用额外驻留空间，避免站在边界附近反复装卸。

预取也有成本。错误预测会占用内存、I/O 和激活队列，挤走真正急需的数据。所以加载优先级应结合到达时间、玩法重要性和资源大小，而不能只按距离排队。

### 地图已经切开，依赖可能又把它连回去了

房屋引用材质，材质引用纹理，任务对象可能引用远处的角色。如果这些引用强制要求目标也驻留，一次局部加载就可能沿依赖关系不断扩张。World Partition 的文档明确指出，相互存在相关 Actor 引用的对象可能被打包在一起加载。[@uePartition]

因此还要检查**依赖闭包**：请求这个区域之后，究竟会一起带入哪些资源。共享资源需要合适的生命周期；跨区域的游戏引用可以考虑稳定 ID 与按需解析，而不是永久持有必须驻留的实例。例如，玩家在 A 区接到任务，目标是 B 区的怪物。任务系统手中持有的不应是怪物的内存指针，而是一个稳定 GUID；当查询进度时，若发现该 GUID 不在活跃内存中，系统便转去读取它的持久化状态记录，从而避免为了一个任务强行将整个 B 区牵连加载。

地图格子只是组织入口。能否真正独立卸载，取决于对象之间如何依赖。

## 让远方可见：几何与纹理的多级表示

玩家登上山顶后，希望看见远处城市。但如果整座城市的室内陈设、门窗交互和角色都随之加载，视距就会变成极昂贵的参数。

远景真正需要提供的是足够准确的画面。我们可以逐步降低表示成本，而不是要求整个远处场景保持完整。

### 先减少看不见的工作，再减少看得见的细节

**可见性裁剪**排除当前视角外或被遮挡的内容；**LOD**为仍需显示的对象选择合适细节；**实例化**则让大量共享几何的对象更便宜地提交和绘制。这几个操作解决不同的浪费。

远处一扇窗只占几个像素时，没有必要用近处同样复杂的几何表达它。但一根细长的高塔虽然很远，仍可能影响轮廓；单纯以世界距离为标准不够，屏幕上的大小、形状和误差也很重要。

**HLOD**进一步把一组静态对象合并或简化为代理。Epic 的 World Partition HLOD 文档明确用它显示完整 cell 尚未加载的远景：原来的对象集合可以卸载，便宜的代理仍然可见。[@ueHLOD]

<RepresentationLayers />

这类代理主要承诺外观。玩家走近后，仍要恢复交互、碰撞与详细状态。房子已经烧毁时，远景若还显示完好的屋顶，就暴露了代理与权威状态之间的一致性问题。

### 从一整个模型，到按需流送几何和纹理细节

Nanite 把网格中的三角形分成小组，称为 cluster，再将这些组组织成层级，按视图选择细节，并按需流送相应数据。它把几何管理推进到了模型内部，使所需驻留的细节更接近当前画面需求。[@ueNanite]

纹理通常预备一组逐级缩小的版本，称为 mip 层级。但一张巨大的贴图只露出其中一个角时，是否仍要加载完整的高分辨率 mip？**Streaming Virtual Texturing** 将各 mip 拆成小 tile，依据可见像素所需的部分，把 tile 放进 GPU 缓存。它需要页表等管理，也有额外采样成本；按渲染反馈请求资源还可能带来细节晚到的现象。[@ueVirtualTexture]

这里最有用的设计认识是：**场景 cell、几何 cluster、纹理 tile，不必是同一种粒度。** 它们分别服务于场景生命周期、几何细节和纹理驻留。AI、网络同步与存档还可以有自己的组织方式。

因此，HLOD、Nanite 和 virtual texturing 可以解决互补的问题。它们不能自动替远处角色决定行动，也不会替磨坊结算库存。优化应落到实际超预算的那一层。

<details>
<summary>世界继续扩大，还会遇到坐标精度问题</summary>

浮点数在更大的数量级上，相邻可表示数之间的间隔也会变大。即使资源已经成功加载，离原点极远时，小幅运动和接触计算仍可能失去所需精度。

经典解法是采用**浮点原点偏移（Floating Origin / World Shift）**，即将整个世界以玩家为中心定期反向平移，保持核心活动区域的局部坐标始终在安全范围内。另一种可选方向是彻底使用更高精度的世界坐标。UE 的 Large World Coordinates 就为核心数据类型引入了双精度支持，并在渲染、粒子等子系统中采用相应表示。[@ueCoordinates]

这也是独立的一笔预算与工程取舍。把坐标改成 double，不能减少活跃对象数；不断进行原点偏移，也需要小心处理平移瞬间的物理状态与残影。

</details>

## 让世界持续变化：少做更新与便宜地更新

接下来假设画面和资源驻留已经可控，但城市里有大量角色，周边还有机器、植物与动物。CPU 的问题是：每一刻到底需要访问谁，做什么？

### 先把更新成本拆开

设一类对象有 $N$ 个，每个对象每秒更新 $f$ 次，每次平均需要 $c$ 秒 CPU 工作。这一类对象每秒就需要约 $Nfc$ 秒 CPU 工作；多类对象相加，得到粗略估算

$$
C\approx\sum_k N_kf_kc_k.
$$

它揭示了三个不同方向：减少需要更新的对象数 $N_k$，减少更新频率 $f_k$，或者降低单次处理成本 $c_k$。

例如，十万个对象每秒更新 $60$ 次，单次即使只花 $2$ 微秒，也需要每秒 $12$ CPU 秒的工作。若其中九万个对象本来就在等待条件变化，让它们反复检查“还没发生”，就不是最值得保留的工作。

这只是说明量级的算例，没有计入调度、缓存失效和并行同步，也不代表某款游戏的性能测量。

### 活动集合与事件驱动：没变化时，少问一次

最朴素的循环会遍历所有对象，再在各自的 `Update` 里判断要不要做事。即使最后什么都没做，遍历、取数据和分支判断也已经发生。

改进办法是维护一个**活动集合**。暂时不会变化的对象退出该集合，把“何时需要重新工作”的条件登记到相关系统。例如磨坊等待原料，就由原料到达通知它；等待下一次生产完成，则登记一个到期时间。调度器只处理已经到期或收到事件的任务。

Factorio 的开发者提供了直接案例：从传送带取物的机械臂，在两条运输线上都无事发生时可以休眠，并登记唤醒关系；物品到来后才重新检查取物。开发日志还讨论了多线程产生唤醒请求时，需要按确定顺序合并，避免更新顺序变化造成不同结果。[@factorio364]

同样的“先登记需求”也能合并重复工作。Factorio 的另一篇日志将雷达覆盖改为区块覆盖计数和分桶更新：重叠覆盖不需要由每座设施反复做相同请求。[@factorio421]

事件驱动的代价是维护依赖关系。原料到达、断电恢复、仓库腾出空间、外部命令，任何一个应当唤醒对象的条件被遗漏，都可能让它永远不再工作。因此适合休眠的对象，需要有清晰、可完整追踪的唤醒条件。

物理引擎的 sleep 是相关但独立的机制。Box2D 会让静止的物体或物体组休眠，在活动物体碰撞它、相关接触或关节被销毁等条件下唤醒。[@box2dSleep] 这依据的是物理状态，而不是物体有没有出现在摄像机里：画面之外仍然可能发生必须正确处理的碰撞。

### 降低频率：把反应时延作为代价

有些对象会缓慢变化，不适合无限休眠，也不需要每帧更新。例如远处行人的路线意图，可以低频重算；附近战斗中的角色则需要及时响应。

可以把对象按重要性分组，给不同组不同的更新周期，再把同一组分散到多帧，避免所有低频任务同一帧到期。距离是一种重要性信号，是否在交战、是否影响任务、是否即将进入玩家范围，也都可以参与判断。

Unreal 的 MassGameplay 将视觉表示、模拟和 replication 的 LOD 分开，其中 simulation LOD 支持可变频率计算，replication LOD 则按客户端分别判断相关性。[@ueMass]

但“把更新频率降十倍”有不同含义。减少 AI 做决策的频率，同时保留运动与碰撞的必要更新，往往比把所有物理步长一起扩大十倍更容易控制。后者可能错过接触或增加数值误差。视觉上的插值能让运动看起来更平滑，却不能补回漏掉的真实交互。

<details>
<summary>另一种稀疏更新：随机挑选少量位置</summary>

并非所有系统都适合给每个对象设置独立计时器。对于大面积的植物生长、环境传播等过程，可以在符合条件的区域中抽样检查。

假设一片区域有 $N$ 格，每轮等概率、独立、有放回地抽 $m$ 次。某格一次没被抽到的概率是 $1-1/N$，因此这一轮至少得到一次机会的概率为

$$
P(\text{被抽到})=1-\left(1-\frac{1}{N}\right)^m.
$$

当 $m$ 远小于 $N$ 时，这约为 $m/N$。候选检查量降到了 $m$；若希望每格得到机会的频率保持接近，抽样数量就要随候选规模增长。

泰拉瑞亚提供了一个具体案例。核对的 PC 1.4.4.5 实现中，`WorldGen.UpdateWorld()` 在地表和地下分别选取跨越世界宽度的随机坐标，再执行对应位置的更新。[@terrariaWorld] tModLoader 的公开补丁将模组回调接在这些入口上，[@tmlWorld] `RandomUpdate` API 用于生长、传播等逻辑。[@tmlRandom]

完整地形可访问，与每格每帧执行更新，是独立的决定。原版快照使用二维 tile 数组，[@terrariaMain] tModLoader 则替换了其存储表示，不能据此推断原版的每格内存布局。[@tmlMain] NPC 也有各自的活动与 despawn 规则；被清理的实例，不等同于休眠后恢复同一个实例。[@tmlNPC]

这个简化概率模型只说明抽样机制。实际更新还受高度、世界类型和对象条件影响；抽中也不等于成功生长。

</details>

### ECS 与数据布局：让确实需要做的工作更便宜

减少更新后，剩下的工作仍可能被内存访问拖慢。如果每个角色都是分散分配的复杂对象，而这一轮只需要位置和速度，CPU 会反复追逐指针、带入不相关字段。

一种做法是按数据和操作组织对象。**ECS** 将实体身份、组件数据和处理这些数据的系统分开；其中一种实现，会把具有同类组件组合的实体成批保存，让系统连续访问自己需要的数组。Unity Entities 的 archetype chunk 就按组件类型放置紧凑数组，并提供按组件组合查询的方式。[@unityArchetypes]

这主要降低前面成本式中的单次处理代价，也方便把独立批次分给多个工作线程。但并行化仍受共享状态和依赖顺序限制；频繁增删组件、在不同分组间搬动实体，也会产生结构变化成本。

这里的 chunk 是内存组织单元，未必对应地图上的一个区块。空间邻近、组件类型相同、使用相同 LOD，是三种不同的分组标准，设计时需要决定它们如何协作。
 
 <details>
 <summary>除了画面，寻路网格（NavMesh）也需要分级流送</summary>
 
 视线之外的区域虽然不需要渲染，但远处的 NPC 可能仍在赶路。大世界极具挑战的一环是：当目标跨入未加载的区块时，AI 如何寻路？
 
 业界常用的做法是建立一套跨越整个世界的“抽象路网（Abstract Graph）”或超大粒度的低精度 NavMesh。远处的商队或 NPC 放弃逐帧物理避障，只在这套极为轻量的抽象路网上推演宏观进度；当它们走进玩家附近的活跃区域时，再无缝切换回基于高精度 NavMesh 的真实物理寻路。这与画面的 LOD 是同等重要的逻辑分级。
 
 </details>

## 让时间跨过细节：补算与分级模拟

上面的办法仍在回答“何时执行原来的逻辑”。更进一步，我们可以问：某段逻辑是否有更便宜的等价结算，或者是否允许用另一种模型表达远处的世界？

### 可以补算的前提：少量状态足以决定结果

给磨坊一个简单规则：每 $30$ 秒生产一袋面粉，原料无限，仓库足够大，没有停电。离开时本轮已经进行 $12$ 秒，世界又经过 $600$ 秒，现在共有 $612$ 秒可结算。

每完整 $30$ 秒产生一袋，因此新增产量为

$$
\left\lfloor\frac{12+600}{30}\right\rfloor=20,
$$

下一轮仍保留 $12$ 秒进度。程序只需记录上次结算时间、进度和产量，不必补跑几万次 tick。

<TimeStrategies />

现在把仓库剩余容量改成七袋，并规定装满后立即停产、不积累停产期间的进度。磨坊只需再运行 $7\times30-12=198$ 秒就会装满，剩下的 $402$ 秒不能继续计入生产。这个约束已经改变了结算结果。

若还存在原料耗尽、停电与季节变化，就需要按相关事件切开时间段。在每个速率和约束保持稳定的区间内结算，再应用边界事件。对于生长速度随环境变化的情况，真正应累计的是

$$
\Delta g=\int_{t_0}^{t_1}r\bigl(e(t)\bigr)\,dt,
$$

其中 $e(t)$ 是当时的环境，$r$ 是对应速率。只拿返回时的温度乘上整个离开时长，会丢掉历史。

在实际工程中，这通常不需要真的去做连续微积分，而是基于**事件切片**。例如系统记录了玩家离开的十分钟内，第 3 分钟发生过一次“下雨”。补算时，程序将这段时间切分为“3 分钟的晴天”和“7 分钟的雨天”两块离散的时间片，分别代入晴天和雨天的速率相加，即可得出最终的准确产量。

还有一个边界：如果磨坊的产物要在离开期间被另一座工厂消耗，就不能毫无通知地等玩家回来才第一次结算。可以在消费者访问库存时推进相关状态，或把生产完成登记为事件；相互依赖的链条需要共同的时间顺序。

**补算所需的不是“玩家没看见”，而是足够的状态、明确的时间规则，以及正确处理外部交互的方式。**

<details>
<summary>案例：饥荒按组件决定休眠期间保留什么</summary>

在核对的饥荒联机版 Lua 脚本中，实体 sleep 会停用 brain、让 state graph 休眠，再分发各组件的回调。这里是引擎对对象活动的管理，与角色睡觉的游戏状态不同。[@dstMain]

`growable` 可以取消生长任务、记录休眠时间并在醒来时长时间更新，也有 `growoffscreen` 分支。[@dstGrowable] `perishable` 则通过约十秒、带少量扰动的周期任务处理腐败，另外提供长时间更新入口。[@dstPerishable] 调度器没有一个因为实体 sleep 就自动取消所有普通任务的统一开关。[@dstScheduler]

因此，一个对象的 AI、腐败和生长不必同进同退。`LongUpdate` 也只是交给明确实现了该方法的组件处理，不会自动推导出所有游戏逻辑的快进规则。[@dstEntity] 具体 prefab 还会介入：例如常青树的休眠处理会移除燃烧、传播等组件，并按条件记录烧毁状态。[@dstEvergreens]

单机版历史脚本还包含跨洞穴恢复时，根据玩家与世界年龄差进行追赶的路径。[@dsCatchup] 联机版则有独立的服务器 shard 和空服暂停配置，离开地面不等于地面服务器已经停止运行。[@dstServer]

这些例子说明，休眠、周期更新、跨时间结算可以组合使用，但其正确性需要落实到具体职责和具体版本。

</details>

### 无法等价补算时，可以改变模拟模型

战斗比磨坊困难。下一次攻击依赖角色位置、上一次碰撞、冷却、目标选择和随机数；中间还可能加入其他角色，桥梁也可能被破坏。只知道起点和经过时间，通常不足以重建这条因果链。

如果玩法允许，可以在远处改用较粗的模型：一个商队不再是十几辆逐帧避障的车，而是一条记录，包含路线、进度、货物、成员身份和途中事件；靠近后再恢复成具体车辆。这是 **simulation LOD** 的另一层含义——不仅减少调用频率，也改变计算的表示。

新的模型应当先声明需要保留什么。对商队而言，货物总量、成员是否存活、行程所处位置可能必须一致；每辆车曾经怎样绕过一块石头，则可以不保留。

<SimulationHandoff />

这不会天然得到与完整模拟相同的所有结果。抽象交战规则可能只保留概率分布或总体趋势；随机事件即使长期分布接近，也不保证某次运行与原始逐步随机序列相同。保留哪些行为精度，是玩法和算法共同作出的选择。

### 恢复细节时，最容易出现“同一份东西变成两份”

将抽象商队恢复成车辆，需要回答三个问题：

1. **身份如何保持**：重要角色应当继续使用稳定 ID，不能每次靠近都变成一个全新的人。
2. **数值如何分配**：抽象库存分配到各车辆后，总量应保持一致，不能凭空多出或少掉货物。
3. **谁继续推进**：交接完成后，抽象层要停止相关结算，避免车辆和抽象记录同时生产、移动或交货。

相反，从细节退回抽象状态时，也要收集尚未完成的工作。正在穿过桥梁、进入战斗或参与玩家交易的对象，可能暂时不适合降低精度。

这形成一种比“距离一到立即切换”更稳健的做法：距离产生切换需求，状态条件决定何时允许切换，转换预算决定每帧实际处理多少。

## 让多个玩家共享世界：相关性与权威边界

### 同一个世界，不同客户端需要不同的内容

设服务器有 $N$ 个对象、$P$ 个连接。若每轮都让每个对象询问每个客户端“你是否需要我”，准备同步本身就可能接近 $NP$ 次判断，即使最后只发出少量数据。

可以先用空间、房间、队伍或其他关系建立候选集合，再筛选必要状态。这类工作通常称为 **interest management** 或 relevancy。一个玩家可能不需要城另一头路人的位置，却需要远程队友的状态、任务目标或已经听见的爆炸。

Unreal 的 Replication Graph 通过持久节点保存、共享并生成各连接所需的 Actor 列表，避免把所有判断都退回逐对象、逐连接的调用。它支持按位置、对象类型、休眠状态和附属关系等方式组织候选列表。[@ueReplication]

候选确定后，还可以控制更新频率与优先级，并只发送必要变化。这里省掉的是网络和同步准备成本；服务器是否继续精细模拟这些对象，是另一个决定。

<details>
<summary>网络休眠与模拟休眠也需要分开</summary>

一个箱子长期不改变库存，网络系统没有必要每轮都比较它的属性。UE 的 network dormancy 可以把这类对象排除在常规复制考虑列表之外，但对象仍可能存在于服务器和客户端。改变需要同步的属性之前，应先正确唤醒或刷新其网络休眠状态，避免变化未被复制。[@ueDormancy]

这与物理物体不再积分、AI 不再思考、整个场景从内存卸载，都不是同一件事。用同一个“sleep”名字概括它们，很容易找错性能瓶颈或唤醒条件。

</details>

### 也可以同步输入，让各端重算世界

如果世界可以确定性地推进，另一条路线是 **deterministic lockstep**：各端拥有相同的起始状态，并按相同顺序执行输入。网络主要传递操作，而不是持续发送所有对象的完整变化。

Factorio 的开发文章说明了这种做法为何适合大量持续活动对象，也解释了不同机器一旦产生不同结果，就会发生 desync。[@factorioLockstep] 但 lockstep 不要求网络拓扑一定是纯 P2P：Factorio 后续的多人重写又专门调整了服务器与客户端之间的通信组织。[@factorioMultiplayer]

它的取舍是让各端承担必要模拟，并严格处理输入顺序、随机数和并行执行的确定性。若某个客户端仅因为自己的摄像机转开，就随意省略会影响世界结果的更新，各端状态便可能分叉。

所以，大量对象不一定意味着持续传输大量状态，但减少状态传输也可能意味着增加本地计算和一致性约束。

### 再加服务器，为什么也不能直接线性扩展

如果一台服务器算不完，可以按区域、场景或实例分配给不同服务。相互作用较少的岛屿很容易分开；所有玩家聚集在同一个战场，或大量对象跨区相互作用时，通信和同步开销就会增加。

尤其要区分：服务器 A 为了判断边界附近的碰撞而保留 B 区域的只读副本，不等于 A 也获得了修改那些对象的权力。**副本可以有多份，某项状态的写入权必须有明确归属。**

玩家或货物跨区时，需要交接状态、所有权与尚未完成的操作。如果采用消息传递，还要考虑重复、延迟与失败恢复，避免双方都认为自己已经交货，或者双方都认为对方会保存。

为了防止产生这类“同一份货物变两份”或凭空消失的幽灵状态，跨区交接通常需要引入明确的设计模式。例如采用类似**两阶段提交（Two-phase commit）**或**所有权锁（Ownership Lock）**的机制：A 服务器先锁定该对象，宣告其处于“正在移交”状态（不再处理常规更新）；随后将数据发给 B；待收到 B 确认接管的回执后，A 再彻底销毁本地实例。任何异常断线都会导致锁回滚，从而保证事实的绝对一致。

这里讨论的是分布式世界必须解决的问题，不是一套只凭“加服务器”就能得到的通用实现。分片能分摊可分离的工作；紧密耦合的交互仍需要协调。

## 让世界记得发生过什么：持久化与状态迁移

### 保存事实，运行时表示按需重建

卸载一个可交互场景前，需要区分持久事实与临时表示。房屋是否烧毁、箱子库存、角色身份、任务阶段，是玩家希望回来后继续成立的事实。动画控制器、渲染代理、寻路缓存，则通常可以从这些事实与资源重新创建。

一种可行的数据表示，是保存稳定 ID、必要组件状态、所属区域、最后结算时刻和数据版本。这样，同一个对象可以经历“精细实体 → 抽象记录 → 存档 → 再次精细实体”，而身份和核心状态不必依赖某次内存分配。

程序生成世界也需要保存变化。若底图可由种子和生成规则重建，可以只记录玩家造成的修改；但生成规则要有版本，否则更新程序后，同一个种子可能重建出不同底图。被删除的对象也需要相应记录，不能因为“存档里没有它”就当作从未生成、重新创造一次。

这些是存储模型的设计选择，并不意味着每款游戏都只存种子和差量；直接保存完整区块也可能更简单、更可靠。

### 快照和增量记录，解决的是不同成本

完整快照让恢复有明确起点，但保存大世界可能很重。只记录变化，可以降低每次写入量，却要承担重放、版本兼容和记录不断增长的管理成本。两者可以组合：定期形成快照，再保存之后发生的修改。

异步保存还要保证读到的是一份自洽状态。假设货物正从 A 仓库转移到 B 仓库，保存线程若先读到转移前的 A，再读到转移后的 B，就可能把同一批货物记两次。可以在一致的逻辑边界冻结或复制待保存数据，再交给后台写入；更复杂的实现可以用版本化读取，获得同一个逻辑时刻的状态。

同理，卸载不是调用一次“删除对象”就结束了：必要修改要已经进入可靠保存流程；迟到的异步任务不能重新激活已被替代的实例；事件订阅和跨区引用也要正确撤销或迁移。

### 到底经过了哪一种时间

“离开十分钟”至少可能指三件事：模拟前进了十分钟、服务器挂钟过了十分钟，或者玩家关闭游戏后现实经过十分钟。它们是否等价，由游戏规则决定。

若使用模拟 tick 作为时钟，暂停期间不应凭空累积生产；若设计了离线收益，就需要另外记录真实时间，并明确速率、上限与外部条件如何处理。持久化的是哪种时间，决定了恢复时能否正确补算。

因此，时间也属于状态协议的一部分。必须与库存、事件顺序和版本一起设计，不能在最后才随手加一个“当前时间减上次时间”。

## 把这些机制拼成一个系统

回到开头的旅行世界。下面是一种**设计示例**，用于展示职责如何组合，并非某个现成引擎自动提供的完整方案。

| 对象 | 完整表示何时需要 | 远处保留什么 | 恢复时必须保持什么 |
| --- | --- | --- | --- |
| 地形与建筑 | 接近交互范围，或预取预测即将到达 | 地形层级、HLOD、持久修改 | 已破坏区域、必要碰撞与视觉一致 |
| 城市行人 | 进入可观察或可交互范围 | 低频路线、日程，必要时只保留群体统计 | 重要角色身份与任务状态 |
| 农田 | 玩家查看、收获或发生外部作用 | 阶段、环境变化事件和结算时间 | 生长条件、产物与剩余进度 |
| 磨坊 | 近处动画与交互；生产需求可持续存在 | 有限库存下的生产事件或按需结算 | 同一份货物和当前生产批次 |
| 商队 | 接近玩家、战斗或复杂交互 | 路线、货物、成员和途中事件 | 身份、总量与唯一的推进职责 |
| 临时粒子与装饰 | 当前视觉需要 | 通常可直接停止或丢弃 | 不承担持久游戏事实 |

一个调度周期可以沿着以下顺序组织：

1. **收集需求**：玩家、摄像机、任务、交互与预测路径需要什么。
2. **解析依赖并排优先级**：完整表示需要哪些资源，哪些必须最先可用。
3. **推进加载与激活队列**：分别遵守内存、I/O、CPU 和转换预算。
4. **运行当前模型**：活动对象、低频组、到期事件和抽象模拟各做自己的工作。
5. **准备各客户端需要的变化**：相关性、重要性和发送预算共同决定同步内容。
6. **提交持久变化并回收资源**：确认状态已经交接，再释放旧表示与失效请求。

具体实现可以流水化、并行化，但依赖关系仍然存在。地面碰撞还没准备好，就不能只因为贴图已经显示而允许玩家落地；抽象商队还在计时交货，就不能让刚生成的车辆再结算一次。

### 需要留出一圈“即将发生作用”的范围

不同系统的边界还要相互协调。玩家的身体当前在这里，下一步运动和弹丸却可能到达更远处；声音、火势、电力或液体，也可能跨过视觉边界。

一种办法是维护交互所需的邻域或提前量。另一种办法是定义明确的跨边界规则，例如把外流量作为事件交给邻区，或在边界处转入较粗模型。无论采用哪种方式，都需要说明遗漏的细节会不会改变玩家关心的结果。

这就是为什么通常不能用一个半径同时控制绘制、碰撞、AI、联网和存档。每个边界服务于不同的依赖，强行对齐反而可能增加成本或破坏正确性。

## 怎样判断方案是否真的更好

比较大世界方案时，先固定它们必须提供的行为。允许远处机器暂停，与要求全球工厂持续生产，负担本来就不同；允许普通路人重新生成，与要求每个人都有永久身份，也不能只拿对象数量比较。

然后分别测量，而不是只看平均 FPS：

| 要检查的目标 | 有用的观察量与场景 |
| --- | --- |
| 稳态成本 | 活跃对象数、各模拟组耗时、GPU 与网络准备耗时 |
| 进入区域的及时性 | 请求到可交互的延迟分布、积压队列、缺失碰撞或资源 |
| 转换是否卡顿 | 高分位帧耗时、单帧激活数量、同时升级 LOD 的峰值 |
| 内存是否稳定 | 稳态与峰值驻留、临时解压缓冲、新旧表示重叠、缓存命中 |
| 状态是否连续 | 库存与身份守恒、任务一致性、跨区交接和恢复后的结果 |

测试路径也要刻意制造压力：高速穿越、突然掉头、远距离传送、很多玩家集中或散开、大批角色同时从抽象状态恢复，以及反复在同一条边界来回移动。

对事件驱动系统，还可以做小规模对照：在同一输入下，比较每步更新与优化后的结果。对时间补算，检查把一段时间拆成几次结算，是否仍满足既定语义；对近似模拟，则应检查它承诺保留的量和统计特征，而不是假设它与详细模型逐步一致。

大世界的核心能力，是让不同部分以合适的成本保有足够的连续性：画面可以是代理，角色可以是低频数据，生产可以是将来到期的事件，远处场景可以只剩存档。真正需要交互时，再把必要细节恢复出来。

空间分区解决组织与驻留，流式加载解决及时到达，多级表示解决细节成本，事件与补算解决时间成本，相关性解决信息分发，权威与持久化解决事实如何延续。理解这些职责及其边界，才能判断一种方案在自己的世界里究竟是否合适。
